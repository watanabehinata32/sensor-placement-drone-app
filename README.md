# センサー配置と災害時ドローン巡回（sensor_app）

企業のお題「新緑県 広域観測網の最適化問題」の一段階目（センサーの配置）と二段階目（災害時のドローン巡回）を、
1 つの Web サイトで解くアプリです。計算は Python（FastAPI）、画面は HTML と JavaScript です。
ソルバーは Fixstars Amplify AE。二段階目は Amplify だけで解く（一段階目だけ、トークンがないとき確認用に手元のタブーサーチ）。

## 起動のしかた（Mac）

```bash
cd sensor_app
python3 -m pip install -r requirements.txt     # 最初の 1 回だけ
cp .env.example .env                            # 最初の 1 回だけ。.env を開いて AMPLIFY_TOKEN= の後ろにトークンを書く
python3 -m uvicorn server.main:app --port 8000
```

ブラウザで http://127.0.0.1:8000 を開きます。止めるときはターミナルで Ctrl + C。
画面右上に「ソルバー: Amplify AE」と出ていれば、トークンが読めています。

## 使い方

1. 最初に「一段階目から」か「二段階目から（厳密解の配置／保存した配置ファイル）」を選ぶ。
2. **① 配置**: 「QUBO で配置を計算」。結果は地図（種類ごとの色とカバー円）と市町村ごとの表に出る。
   「配置をファイルに保存」で placement.json に保存でき、あとで読み込める。
3. **② 被害**: 地図のクリックで通行止め（道路）と通信断（センサー）を切り替える。震源を置いてまとめてつくることもできる。
   最初はサンプルの地震（資料 p.6 の図から読み取ったもの）が入っている。車・バッテリー・QUBO の重みは「詳しい設定」。
4. 「ドローンの巡回を計算」→ **③ 結果**: 車ごとの走行ルート・ドローンの飛行・回復時刻と、車ごとの時刻表。
   地図の下の ▶ とスライダーで、車（道路の速さどおり）とドローン（🛸）の動きを再生できる（1・5・10 倍）。
   センサーは回復した時刻に赤から緑に変わり、左上に「○○分：回復 n 基」と車ごとの状態が出る。時刻表の横棒を押すとその時刻へ飛ぶ。
   「被害を変える」で ② に戻って解き直せる。① をやり直すと、設置しなくなったセンサーは通信断から外れる（知らせが出る）。

## 初期値と判定

- 一段階目: マス目 500 m・λ_cov 4・制限時間 5000 ミリ秒・罰則（1 地点 1 台、α・β）は重みなし（= 1）。
  前回の公開版（Render、GitHub の Optimal-Sensor-Placement-in-Two-Dimensions）と同じ。
  中央市のカバー率下限は元データの 100% から 95% に下げている。センサー性能表・市町村の必要値表は「詳しい設定」で変えられる。
- 判定はゆるみなし（カバー率が下限に少しでも届かなければ ✗）。前回の版にあった「0.1 ポイントまでおまけ」はやめた。
- 二段階目: Amplify の制限時間 3000 ミリ秒で ④ルートの選択 を 1 回解く（②は今は飛ばしている）。前提は次の「二段階目で置いている仮定」。

| 場所 | 中身 |

| `server/settings.py` | .env からトークンを読む |

| `core/preprocess.py` | 二段階目 ① 前処理（走行時間・届く離陸地点・飛行の数え上げ・対応不能の判定） |
| `core/phase2.py` | 二段階目 ② 飛行の選択 QUBO → ③ ルートの数え上げ → ④ ルートの選択 QUBO → ⑤ 後処理 |
| `core/routing.py` | 時間の数え方（走行・準備・充電）と、ルートから予定表を作る評価 |

## 窓口（API）の一覧

| 窓口 | すること |
|---|---|
| GET `/api/map` | 地図データ（県・市町村・候補地点・道路・拠点・凡例の色）とサンプルの被害 |
| POST `/api/phase1/solve` | 一段階目を解く |
| POST `/api/phase1/check` | 読み込んだ配置のコストと達成状況 |
| GET `/api/phase1/exact` | 厳密解の配置（保存ファイルを読むだけ） |
| POST `/api/damage` | 震源から被害をつくる |
| POST `/api/preprocess` | ドローンで届かないセンサーの判定 |
| POST `/api/phase2/solve` → GET `/api/phase2/jobs/{番号}` | 二段階目を解く（受付番号で進み具合を問い合わせる） |

## 二段階目で置いている仮定（2026-11-11 時点）

先方のお題に書かれていない点や、こちらで決めた点。値は `core/config.py` と `phase2_roads_company/loader_config.json`。

**ドローン**
- 速度 40 km/h、1 回の飛行は 15 分まで。センサーの真上で 3 分滞空した時点で「回復」とする。
- 離陸地点からセンサーまでは直線で飛び、同じ離陸地点に戻る。
- 1 回の飛行で回るセンサーは 1 基（今のデータでは、2 基を 15 分で回れる組が無い）。
- 片道の届く距離は約 4 km（(15 分 − 3 分) × 40 km/h ÷ 2）。どの離陸地点からも届かないセンサーは「対応不能」として外す。

**車と離陸地点**
- 車は 8 台（県庁 4・西南市役所 2・北東町役場 2）。最後は自分の拠点に戻る。同じ拠点の車は性能が同じとして扱う。
- 走る速さは道路の種類で決める（高速 60・ランプ 30・国道 40・主要地方道 30・一般県道 20 km/h）。通行止めの区間は通らない。
- 離陸できるのは国道・主要地方道・一般県道の上だけ（高速道路では止まれない）。候補は 250 m おき（区間の端と、センサーに最も近い点も加える）。
- 離陸地点に着いてから離陸まで、準備に 10 分かかる。

**バッテリー**
- 着陸後、次に飛ぶまで充電 30 分。充電は走行中・準備中も進む（次の離陸までの待ちは「充電 30 分」と「走行 ＋ 準備 10 分」の長い方）。
- 1 台が飛べる回数はバッテリーで 5 回まで（お題の「内蔵 4 回」を「出発時の満充電 1 回 ＋ 充電 4 回」と読んだ）。
- 予備バッテリーは扱わない（お題には全体で 1 個とあるが、一旦外した）。
- 1 台が飛ぶ最大回数は自動で決める：回れるセンサー数 ÷ 台数 の切り上げ ＋ 1、上限 5 回（サンプルでは 3 回）。

**解き方**
- ②飛行の選択（集合被覆）は今は飛ばし、①で見つけた離陸地点を全部 ③ で使う。
- ③ではルートを拠点ごとに作り、回るセンサーの組が同じなら「最後の回復」が一番早い 1 本だけ残す。
- ④の式：H ＝ A ×（未回収の数）＋（各ルートの最後の回復時刻³ の合計、時間単位）＋ λ ×（各拠点で選ぶルートが台数以下、の罰則）＋ λ ×（各センサーはちょうど 1 回、の罰則）。
  お題の目的①（回復数を最大）は A で、目的②（最後の回復時刻を最小）は 3 乗の合計で近づけている（最後の回復時刻そのものを最小にする式ではない）。
- どの車がどのルートを走るかは、⑤で拠点ごとに 1 号車から順に割り当てる。

## わかっている課題

- 回れなかったセンサーは付け足さず、③ に「⚠ 未回収」と出す。決まり（罰則）を守れていない所も ③ に出す。
- 1 台が飛ぶ最大回数が 4・5 回になる大きな被害では、ルートの候補が数千〜1 万本に増えて重くなる（サンプル 3 回なら 1,407 本）。
- サンプル地震（Mac・Amplify 1 回、2026-11-11）：14 基すべて回収・違反なし、最後の回復 142.62 分・全車帰着 207.26 分。
